## 2. 먼저 막아야 할 것 — 크롤링 법적 위험

**채용 플랫폼을 통째로 긁어오지 않는다.** 근거:

- 사람인이 잡코리아 채용정보를 크롤링해 쓴 사건에서 법원은 **데이터베이스 제작자 권리 침해**를 인정했다 (서울고법 2017.4.6. 선고 2016나2019365, 손해배상 인정). 보도에 따르면 이후 합의금이 120억 원대였다.
- 크롤링의 법적 쟁점은 정보통신망 침입 · 데이터베이스권 침해 · 부정경쟁행위 세 가지다.

→ 사람인 · 잡코리아 · 원티드 · 점핏 같은 **플랫폼 목록 페이지 대량 수집은 하지 않는다** (종합 문서 6.4의 결정 유지).

## 3. 설계

### 3.1 기술 사전 — 하나로 세 기능을 돌린다

`lib/techDictionary.ts` (신규). 지금 `lib/github.ts`의 `NPM_MAP` 등을 흡수해 **공고 추출과 레포 감지가 같은 사전**을 쓴다.

```ts
{
  id: "threejs",
  name: "Three.js",
  category: "frontend-graphics",
  aliases: ["three.js", "threejs", "three js", "R3F", "react-three-fiber"], // 공고 문장에서 찾을 말
  detect: { npm: ["three", "@react-three/fiber"] },                         // 레포에서 찾을 근거
}
{
  id: "ssr-streaming",
  name: "SSR Streaming",
  category: "frontend-rendering",
  aliases: ["SSR", "서버 사이드 렌더링", "Streaming SSR", "스트리밍"],
  detect: { npm: ["next"], files: ["app/**/loading.tsx"], code: ["<Suspense", "renderToPipeableStream"] },
}
```

- 처음엔 **약 150개** (언어 · 프레임워크 · DB · 인프라 + 우대에 자주 나오는 개념: SSR · WebGL · MSA · Kafka · K8s · 테스트 · CI/CD …)
- 공고에서 사전에 없는 영문 기술명이 반복되면 **"미등록 후보"로 수집 PR에 표시** → 사람이 확인 후 사전에 추가 (트렌드 수집과 같은 방식)
- `detect.code`는 파일 내용을 봐야 해서 비용이 크다 → 1차는 `npm` · 설정 파일 · 파일 경로만, 코드 패턴은 S3의 `FrameworkSignalDetector`(자산화 계획)와 합친다

### 3.2 공고 → 필수 / 우대 분리 (규칙)

1. HTML → 텍스트
2. 제목 패턴으로 구역 나누기: `자격 요건|필수|Requirements` / `우대|Preferred|Nice to have` / `주요 업무|담당 업무`
3. 구역별로 사전 매칭 → `required[]`, `preferred[]`, `mentioned[]`(구역 못 찾음)
4. 구역 제목을 못 찾으면 전부 `mentioned`로 — **AI로 추측하지 않는다**

### 3.3 기능 A — 공고 링크 분석

- Route Handler `POST /api/jobs/analyze` `{ url } | { text }`
- **보안 (신뢰 경계):** http/https만, 사설 IP · localhost 차단(SSRF), 응답 2MB · 5초 제한, 리다이렉트 3회
- 원티드처럼 JS로 그리는 페이지는 본문이 비어 온다 → **"본문을 붙여넣어 주세요"** 로 대체 입력
- 결과: 필수 · 우대 기술 + **내 분석 결과와 비교** (내 레포에 있음 ✅ / 없음 ☐ / 근거 파일)

### 3.4 기능 B — 월간 수집 → 채용 트렌드

이미 있는 파이프라인을 그대로 쓴다 (`scripts/collect-trends.ts` + `.github/workflows/collect-trends.yml`).

```
매달 2일 GitHub Actions
  → scripts/collect-jobs.ts (출처 ②③④, 개발 직군만)
  → data/trends/jobs/YYYY-MM.json
  → PR 생성 + Discord 알림 (지금 GitHub 트렌드와 같은 형식)
  → 사람이 확인 → 머지 = 반영
```

```ts
type JobTrendSnapshot = {
  period: "2026-11";
  collectedAt: string;
  sources: { name: string; url: string; postings: number }[]; // 출처별 공고 수
  postings: { company; title; url; deadline; required: string[]; preferred: string[] }[];
  unknownTerms: { term: string; count: number }[];             // 사전 등록 후보
};
```

**화면** (`/trends`, 기존 페이지에 섹션 추가):
- 기술별 공고 수 Top 15 — 필수 / 우대 막대를 나눠서
- **우대 기술 Top 10** (Three.js · SSR Streaming 같은 것이 여기 나온다)
- 회사별 기술 스택 카드 (회사 → 자주 나오는 기술)
- 지난달 대비 변화
- 모든 지표 아래: **"N개 기업 · M개 공고 기준, 출처 · 수집일"** — 시장 전체가 아니라는 걸 숨기지 않는다

### 3.5 기능 C — 우대 기술 ↔ 내 레포

- 내 GitHub 분석 결과(이미 저장됨)의 의존성 · 파일 목록에 사전의 `detect`를 돌린다
- 결과는 레포 분석과 같은 모양: **있음 = 근거 파일 경로**, 없음 = 할 일 후보
- 할 일 목록에 넣을 땐 **🤖 제안**으로 구분 (규칙 판정 ✅와 섞지 않음): "카카오 · 토스 프론트 공고 6건 중 4건이 SSR을 우대 → 작은 Next.js App Router 예제로 경험을 남겨 보세요"
- 개수는 코드가 세고, AI는 문장만

### 결론

| 등급 | 출처 | 판단 | 얻는 것 |

| **바로 사용** | **Greenhouse 공개 채용 API** — 당근 · 쿠팡 · 크래프톤 · 몰로코 | 회사가 공개 게시용으로 연 API (인증 없음, `boards-api.greenhouse.io/v1/boards/{회사}/jobs?content=true`) | **공고 본문 전체** → 필수 / 우대 분리 가능. 개발 공고 약 120건 (당근 31 · 쿠팡 약 68 · 크래프톤 16 · 몰로코 7) |

| 제외 | 카카오 · 우아한형제들 · 토스 · NHN · 현대 · LG 채용 페이지 | JS로 그려서 공개 문서 없는 내부 API를 써야 함. 우아한형제들은 robots.txt가 내부 API 경로(`/w1/`)를 막음 | — |
| 제외 | 고용24 채용정보 API | **기업회원 전용** (사업자등록번호 필요로 안내됨) — 학생 팀은 신청 불가 | — |

### 그래서 바뀌는 것

- 기능 B는 **두 층**으로 보여준다: ① 사람인 keyword로 "시장 전체 기술 빈도" ② Greenhouse 기업 본문으로 "주요 기업의 필수 · 우대 기술". 화면에 출처와 표본 수를 따로 표시한다.
- **우대 기술(Three.js · SSR Streaming)은 본문이 있는 출처에서만** 나온다 → 1차는 Greenhouse 4곳 + 기능 A(사용자가 붙여넣은 공고).
- 쿠팡은 "개발"이 들어간 비개발 공고(사업개발 등)가 섞인다 → 직군 분류는 공고 제목 키워드 + Greenhouse `departments` 필드로.
- 다른 회사의 Greenhouse · Lever 사용 여부는 수집 스크립트에서 회사 목록만 늘리면 된다 (오늘 확인: 하이퍼커넥트 · 토스 · 무신사 · 컬리 · 야놀자 · 라인은 Greenhouse · Lever 없음).

## 6. 발표에서 쓰는 법

- 트렌드 지표는 "**코드가 모으고 → 사람이 PR로 확인하고 → 출처와 함께 보여준다**" — 교수님의 "근거" 질문에 대한 답과 같은 구조

- 크롤링 판례를 먼저 확인하고 출처를 고른 것 자체가 설계 판단으로 말할 거리
