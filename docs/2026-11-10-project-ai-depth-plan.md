| 칸 | 지금 결과 | 원인 (코드 확인) |
|---|---|---|

| 6 결과 · 지표 | "테스트 유무: true, 커밋 수: 34" — 날것 | 코드가 넘긴 facts를 AI가 그대로 옮김. 규칙으로 만들 수 있는 칸을 AI에 맡김 |
| 7 회고 | 빈 칸 | README에 회고가 없으면 비움 (맞는 동작). 대신 "이걸 생각해 보세요" 같은 도움도 없음 |
| 탭 3개 | 구현 설명 · 면접 연습 · 기술 추천 비활성 | S2 · S3 미착수 (`ProjectsTab.tsx:15`) |

**근본 원인 하나:** 백엔드 `GET /api/github/repo-context`가 README · 설정 파일 · 파일 경로 목록 · 커밋 첫 줄(최대 100개)만 준다 (`RepoContextResponse.java`). **코드 내용과 커밋 변경 내용(diff)이 없다.** 프롬프트를 아무리 고쳐도 재료가 없으면 자세해질 수 없다.

→ 그래서 순서는 **① 재료(컨텍스트) 늘리기 → ② 카드 프롬프트 다시 쓰기 → ③ 그 재료로 탭 3개 열기.** 세 탭 모두 같은 재료를 쓴다.

## 2. P1 — 레포 컨텍스트 확장 (백엔드, 모든 기능의 기반)

`RepoContextResponse`에 3개를 추가한다. 이름은 자산화 기획의 `RepoContextCollector` · `KeyFileSelector` · `ContributionAnalyzer`를 따른다.

| 추가 | 내용 | 고르는 규칙 (AI 아님) | GitHub 호출 |
|---|---|---|---|
| `keyFiles` | 핵심 파일 **내용** 최대 10개, 파일당 3,000자 | 경로 패턴 점수: 화면 · 라우트(`app/**/page`, `pages/`, `routes`), API · 컨트롤러 · 서비스, 상태 · 컨텍스트, 진입점(`main`, `App`) + **내가 많이 고친 파일** 가산. 테스트 · 설정 · 생성물 · lock 제외 | 최대 10 |
| `myFiles` | 내가 고친 파일 · 폴더 상위 10개와 각 커밋 수 | `/commits?author={내 login}`으로 **내 커밋만** 받아(최근 100개 중 섞인 것이 아니라) 최근 30개의 변경 파일을 폴더 단위로 집계 | 1 + 최대 30 |
| `fixCandidates` | 문제 해결 후보 커밋 3개의 **변경 내용** (파일 목록 + patch 앞부분 2,000자) | 지금의 `FIX_COMMIT` 정규식으로 후보 최대 10개 → 상세를 받아 변경 줄 수 10~400줄인 것 중 최근 3개 (줄 수는 상세를 받아야 알 수 있다) | 최대 10 |

- 호출 합계 레포당 약 55회 — 사용자 토큰 기준 시간당 5,000회 한도에 여유. **`pushedAt`이 바뀌었을 때만 다시 수집**하고 결과는 프로젝트별로 저장 (같은 레포를 매번 긁지 않음). `myFiles`는 이미 있는 `project.contribution_json` 컬럼(S2용으로 비워 둠)에 저장
- AI에 보내는 양: 약 4만 자 이내. 비용은 gpt-4o-mini 공시 단가 기준 **호출당 5원 안팎으로 추정** — 착수 시 실측
- **공개 레포만 읽는다.** 연동 토큰 scope가 `public_repo`라서 비공개 레포 코드는 애초에 읽을 수 없다 (`OAuthService.java:122`). 지금처럼 본인 프로젝트만 조회 (타인 접근 404 유지)
- **보내기 전에 코드가 가린다 (필수, 신뢰 경계):** `.env*` · `*.pem` · `*.key` · `secrets` 경로는 `keyFiles` 후보에서 제외, 내용 중 키 형태 문자열(`sk-…`, `AKIA…`, `ghp_…`, `-----BEGIN … KEY-----`)은 `[가림]`으로 치환. patch도 같은 처리
- 커밋 작성자가 GitHub 계정과 연결 안 된 이메일이면 `author`가 null이라 내 커밋으로 안 잡힌다 (`GitHubService.java:155`) → `myFiles`가 비면 화면에 "Git 커밋 이메일을 GitHub 계정에 등록하세요" 안내

## 3. P2 — 정리 카드 다시 쓰기

### 3.1 칸별 변경

| 칸 | 바꾸는 것 | 누가 쓰나 |
|---|---|---|
| 2 내 역할 | `myFiles`로 "src/app/diary · src/components 중심, 커밋 34개 모두 본인 (1인 개발)" + 내 커밋에서 기능 2~3개를 구체적으로. 2~4문장 | 수치 · 영역은 **코드가 문장 틀로**, AI는 기능 서술만 |
| 3 핵심 기능 | `keyFiles` 내용을 보고 "무엇을 · 어떻게(사용한 API · 라이브러리 · 핵심 로직)" 2~3문장. 근거 경로 검증은 지금처럼 유지 | AI + 경로 검증 |
| 4 기술 선택 | 이유는 계속 **지어내지 않음**. 대신 ① 코드에서 확인한 사실("Next.js App Router · TMDB API · Firebase Auth 사용") ② 스스로 답할 질문 3개를 **저장**해서 새로고침해도 남게 | 사실은 코드(사전 `lib/jobTech.ts`의 `npm` 감지), 질문은 AI |
| 5 문제 해결 | `fixCandidates`의 실제 변경 내용으로 문제 → 원인 → 해결 → 결과. **근거 커밋(sha · 파일)을 칸 아래에 링크**. ("다른 커밋으로 다시 쓰기" 칩은 2차) | AI + 커밋 sha가 후보에 있는지 검증 |
| 6 결과 · 지표 | **AI를 빼고 규칙으로**: "배포: yeflix-diary.vercel.app · 테스트 파일 있음 (3개) · CI 없음 · 커밋 34개 (기간 3개월)" + README에 숫자가 있으면 그 문장 인용 | 코드 |
| 7 회고 | README에 없으면 비우되, **회고 질문 3개**를 저장해 보여줌 (예: "테스트 없이 34번 커밋했는데, 다시 하면 어디부터 테스트하겠어요?" — 레포 점검 결과에서) | 질문만 AI, 근거는 점검 결과 |

### 3.2 바뀌는 규칙

- **화면에 남아야 할 AI 보조 정보 저장:** 비운 이유(`skipped`), 기술 비교(`techCompare`), 회고 질문 → 백엔드 카드에 `hints` JSON 한 칸 추가. 지금은 컴포넌트 상태라 새로고침하면 사라진다 (`ProjectCardEditor.tsx:30`)
- **분량 지시:** 칸마다 문장 수 · 꼭 들어갈 요소(파일 이름 · 화면 이름 · 라이브러리)를 프롬프트에 명시
- **검증 추가:** 3칸 근거 경로(지금 있음) + 5칸 커밋 sha가 후보에 있는지 + 2 · 6칸 숫자는 코드가 넣으므로 AI 숫자 무시
- 프롬프트는 지금처럼 `system`(지시) / `user`(데이터) 분리 유지

## 5. P4 — 면접 연습 탭

- **질문 재료:** 내가 고친 파일(`myFiles`) · 핵심 파일 내용 · 문제 해결 커밋 · 카드 내용 · 사용 프레임워크
- **유형:** 내 코드("`AuthContext`에서 로그인 상태를 어떻게 유지했나요?") · 프레임워크 · 트러블슈팅 · 기술 선택 · 확장 — 질문마다 **근거 파일 / 커밋 표시**
- **채점하지 않는다.** 답 입력 → "좋은 답에 들어갈 요소" 펼쳐 보기 → 연습 기록 저장. AI가 정답을 판정하는 상황을 만들지 않음 (발표 Q&A의 신뢰 답변과 같은 원칙)
- 질문 은행을 한 번 만들고(`QUESTION_BANK`) 5문제씩 꺼냄 → AI 호출은 레포가 바뀔 때만

## 6. P5 — 기술 추천 탭 (채용 트렌드와 연결)

- **새로 생긴 연결고리:** `lib/jobTech.ts` 사전 + 채용공고 우대 기술 집계(job-trends 계획 기능 B)
- 규칙: "내 희망 직무 공고의 우대 기술 상위" − "내 레포에서 감지된 기술"(사전 `npm`) = 추천 후보. 예: "프론트 공고 우대 1위 SSR — yeflix는 클라이언트 렌더링만 사용"
- AI는 후보마다 **이 프로젝트에 붙이는 첫 단계** 한두 문장만 (후보 목록에 없는 기술을 내면 버림)
- [해봤어요] 체크 → 다음 분석 때 레포에서 감지되면 자동 ✅
- 공고 수집(job-trends 4번)이 늦어지면 1차는 사전의 카테고리 + 레포 점검 결과(테스트 · CI 없음)만으로 추천

## 9. 검토 기록 (2026.11.10, 코드 대조)

| # | 지적 | 근거 | 반영 |
|---|---|---|---|
| 1 | "비공개 레포도 읽을 수 있다"는 **틀림** | 연동 scope가 `read:user,user:email,public_repo` (`OAuthService.java:122`) | 2장 수정 — 공개 레포만 |
| 2 | 내 커밋을 "최근 100개 중 내 것"으로 고르면 큰 팀 레포에서 내 커밋이 빠질 수 있음 | 지금 수집은 `/commits?per_page=100` | `?author=` 필터로 내 커밋만 받기 |
| 3 | 문제 해결 후보의 "변경 줄 수"는 상세를 받아야 알 수 있어 호출 3회로 안 끝남 | GitHub 커밋 목록 응답에는 stats가 없음 | 후보 10개 상세 → 3개 선택, 호출 수 45 → 55 |
| 4 | 비밀값 가림이 "결정할 것"에만 있었음 — 신뢰 경계라 선택 사항이 아님 | 코드 · patch를 외부 AI로 보냄 | 2장 필수 규칙으로 올림 |
| 5 | 기여 저장 칸을 새로 만들 필요 없음 | `project.contribution_json`이 이미 있고 비어 있음 (`Project.java:48`) | 그 칸 사용 |
| 6 | 개선 전 결과가 없으면 "더 자세해졌다"를 증명 못 함 | 골든셋 평가가 2번 뒤에만 있었음 | 0번 "기준선 저장" 추가 |
| 7 | Git 이메일 미연결이면 내 커밋 0개 | `author.login`이 null (`GitHubService.java:155`) | 안내 문구 추가 |
| 8 | 비용 "1~2원"은 근거 없음 | 4만 자 ≈ 수만 토큰 | "5원 안팎 추정, 실측"으로 수정 |
