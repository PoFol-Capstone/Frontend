## 0. 먼저 — 갈아엎는 게 아니다

| 구분 | 바뀌는가 |
| --- | --- |
| **핵심** (레포 분석 · 피드백 · 트렌드) | **그대로** — 이미 1 · 2차 구현이 있고 방향도 맞다 |
| 팀원 모집 | 삭제 |
| 게시판 | 메인에서 제외, 대신 공개 포트폴리오 링크 (2.3) |
| 기업 공고 · 교육 · 프로젝트 | **새로 추가** — 핵심 기능과 연결되는 형태로 |

바뀌는 건 **주변 기능 3개**다. 기획서의 "본인 레포 피드백 사이트"라는 중심은 흔들리지 않는다.
오히려 팀원 모집을 빼면 "커뮤니티가 있어야 돌아가는 기능"이 하나 더 줄어서 방향이 더 선명해진다.

## 1. 팀원 모집 — 삭제

### 1.1 문제

| 문제 | 내용 |
| --- | --- |
| **신뢰** | 처음 온 사람은 이 프로젝트가 나에게 도움이 될지, 모집자가 끝까지 할 사람인지 판단할 근거가 없다 |
| **완주율** | 사이드 프로젝트는 시작 후 얼마 안 가 멈추는 경우가 많고, 중도 이탈과 공석이 반복된다는 지적이 많다 [R1][R2] |
| **더 나은 대안이 있다** | 정부 · 기업이 주최하는 프로젝트(예: 미래내일 일경험 프로젝트형 — 4인 내외 팀이 실전 과제를 하고 전문가 코칭을 받음 [R3])는 주최자가 분명하고, 결과가 경력으로 인정되기 쉽다 |
| **콜드 스타트** | 모집 글도, 지원자도 사용자가 많아야 생긴다 (기획서 2.2 ①과 같은 문제) |
| **경쟁** | 인프런 등 이미 모집 게시판이 많다 [R4] |

> 결론: 학생에게 "검증 안 된 팀 프로젝트"보다 "주최자가 있는 기업 · 정부 프로젝트"를 연결해 주는 게 더 도움이 된다.
> 팀원 모집은 삭제하고, 그 자리를 **기회 피드(3장)** 로 채운다.

### 1.2 삭제 범위 — 생각보다 넓다

팀원 모집은 게시글(Post)에 섞여 있다. 게시글 종류가 `RECRUIT` / `DISPLAY`로 나뉘고, 지원 · 지원자 관리 · 알림이 모두 여기에 붙어 있다.

| 영역 | 파일 (확인한 것) |
| --- | --- |
| 프론트 — 모집 관리 화면 | `app/[locale]/recruitment/*` (페이지, 액션, 컴포넌트 8개) |
| 프론트 — 게시글 상세 | `ApplicationSection`, `ApplyModal`, `EditApplyModal`, `ViewApplyModal`, `PositionSelector`, `PostDetail/*` |
| 프론트 — 글쓰기 · 수정 | `TeamRecruitSection`, `board/write/page.tsx`, `EditPostClient` |
| 프론트 — 진입점 | `ProfileMenu`(모집 관리 메뉴), 게시판 카테고리 `"Recruiting"`(`categories.ts`, `CategoryFilter`), 홈 `page.tsx` |
| 프론트 — 공용 | `lib/apply.ts`, `lib/recruitPositions.ts`, `lib/post.ts`, `lib/postContent.ts`, `types/post.ts` |
| 백엔드 | `domain/apply/*`(지원 엔티티 · 서비스 · 컨트롤러), `Post`의 모집 필드, `PostType.RECRUIT`, `RecruitPosition`, 알림 타입, 메일 |

### 1.3 삭제 방법 — 2단계 추천

| 단계 | 할 일 | 이유 |
| --- | --- | --- |
| **1단계: 숨김** | 진입점만 제거 — 프로필 메뉴의 모집 관리, 게시판 "Recruiting" 카테고리, 글쓰기의 팀원 모집 섹션, `/recruitment` 접근 시 게시판으로 이동. 기존 모집 글은 일반 글처럼 보이게 (지원 버튼만 숨김) | 작업이 작고 되돌릴 수 있다. 기존 데이터를 건드리지 않는다 |
| **2단계: 코드 삭제** | 1단계 후 문제가 없으면 프론트 컴포넌트 · 백엔드 `apply` 도메인 · 모집 필드 제거, DB 마이그레이션 | 구조 정리. 발표 전 코드 정리가 필요할 때 |

- 기존 모집 글 · 지원 데이터를 지울지 남길지는 따로 정한다 (실사용자 데이터가 있다면 남기는 것을 추천).

## 2. 게시판 — 무엇으로 바꿀까

### 2.1 선택지

| 안 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| **A. 순수 커뮤니티** | "개발 어렵다", 취업 고민, 질문 등 자유 글 | 글쓰기 장벽이 낮다 | **기획서 2.2의 콜드 스타트 문제가 그대로 다시 생긴다.** 빈 게시판은 여전히 다시 오지 않을 이유가 된다. 에브리타임 · 오픈채팅 · 개발자 커뮤니티와 직접 경쟁. 신고 · 운영 부담 |
| **B. 레포 연결 질문** | 질문할 때 내 분석 결과나 레포 카드를 붙일 수 있음 ("이 레포 README 어떻게 고칠까요?") | 핵심 기능과 이어진다. 답하는 사람이 맥락을 바로 본다 | 답해 줄 사람이 있어야 한다 (콜드 스타트는 남음) |
| **C. 프로젝트 카드 공개 피드** | 분석 → 정리된 프로젝트 카드를 공개하면 피드에 올라감 (글을 새로 쓰지 않음) | **사용자가 혼자 써도 콘텐츠가 쌓인다.** 다른 사람의 정리된 프로젝트 = 참고 자료 | 소통 기능은 약하다 |

### 2.2 C안 재검토 — "올려서 뭐하지?"

처음엔 C를 추천했지만 다시 따져 보니 **올리는 사람이 얻는 게 없다.**

| 올릴 이유 | 현실 |
| --- | --- |
| 남들이 봐준다 | 보는 사람이 없으면 성립 안 함 (커뮤니티를 포기한 이유와 같음) |
| 서로 피드백 | 피드백할 사람이 있어야 하고, 학생끼리의 피드백은 질이 낮음 (기획서 2.2 ③) |
| 다른 사람 프로젝트 참고 | 보는 사람에게만 이득, 올리는 사람에게는 이득 없음 |

C안은 "콘텐츠가 쌓인다"는 **운영자 입장**만 본 판단이었다.

### 2.3 결론 — 피드 대신 "공개 포트폴리오 링크", 게시판은 메인에서 제외

사람들이 velog · 노션 포트폴리오 · GitHub README를 공개하는 이유는 누가 피드에서 봐줘서가 아니라
**이력서 · 지원서에 붙일 주소가 필요해서**다.

- **만들 것: 공개 포트폴리오 페이지.** 정리된 프로젝트 카드 + 분석 결과를 링크 하나로 지원서에 낸다.
  보는 사람은 채용 담당자, 공개하는 이유는 본인 지원 → 다른 사용자가 없어도 가치가 있다.
  이미 `/profile/[id]`(공개 설정 항목만 노출)가 있어서 지원서용으로 다듬기만 하면 된다.
- **피드는 지금 만들지 않는다.** 공개 페이지가 쌓이고 사용자가 생기면 그때 모아 보여주기를 검토한다.
- **사람끼리 피드백도 지금은 넣지 않는다.** 피드백은 AI 분석이 맡는다.
- **게시판(질문 · 고민 포함)은 메인 메뉴에서 뺀다.** 기존 글 · 데이터는 남겨 두고, 사용자가 생긴 뒤 다시 판단한다.

## 3. 기회 피드 — 기업 · 정부 공고, 교육, 프로젝트 연결 (신규)

### 3.1 왜 좋은가

| 이유 | 내용 |
| --- | --- |
| **신뢰** | 주최자가 기업 · 정부 기관이라 "도움이 될까?"라는 의심이 적다 |
| **재방문 이유** | 공고는 계속 새로 올라오고 마감이 있다 → 사용자가 주기적으로 확인할 이유 (커뮤니티 없이도 생기는 재방문) |
| **핵심 기능과 연결** | 레포 분석 결과(언어 · 프레임워크)로 **내 스택에 맞는 기회**를 먼저 보여준다. 지원 전에 "레포 점검 체크리스트"로 이어진다 |
| **콜드 스타트 없음** | 콘텐츠를 사용자가 아니라 외부 데이터가 채운다 |

### 3.2 무엇을 보여줄까

| 종류 | 예 |
| --- | --- |
| 정부 지원 일경험 · 프로젝트 | 미래내일 일경험(프로젝트형 · 인턴형), 청년 일경험 사업 |
| 기업 교육 · 부트캠프 | 기업이 운영하는 SW 교육, K-디지털 트레이닝 과정 |
| 기업 챌린지 · 해커톤 · 공모전 | 기업 주최 개발 대회 |
| 인턴 · 신입 공고 (선택) | 개발 직군 인턴 · 신입 |

### 3.3 데이터를 어디서 받나

| 출처 | 방식 | 상태 · 주의 |
| --- | --- | --- |
| **온통청년 청년정책 API** (한국고용정보원) | 공공데이터포털 Open API, JSON/XML, 무료, 활용신청 필요 [R5][R6] | 청년 일자리 · 교육 정책을 키워드 · 분류로 검색 가능. 개발 직군만 따로 걸러야 함 |
| **정부지원일자리 참여자모집정보 API** (한국고용정보원) | 공공데이터포털 Open API [R7][R8] | 모집 공고 목록 · 상세(마감일, 직무, 인원). 재정지원 일자리 전반이라 **개발 직군 비중은 낮을 수 있음** — 실제 데이터를 받아 보고 판단 |
| 고용24 훈련과정 (K-디지털 트레이닝 등) | Open API 명세를 이번 조사에서 확인하지 못함 [R9] | 공공데이터포털 · 고용24에서 명세 확인 필요 |
| 청년일경험 포털 (미래내일 일경험) | API 확인 못 함 | 우선 수동 등록 + 원문 링크 |
| 기업 교육 · 해커톤 | 연 수십 건 수준 | **수동 큐레이션 JSON** (트렌드 지표와 같은 방식, 검토 문서 3.2) |
| 사람인 · 잡코리아 · 대외활동 사이트 | 약관 · 공식 API 이용 조건 미확인 [R10] | **확인 전까지 크롤링하지 않는다** |

### 3.4 단계별 계획 (안)

| 단계 | 범위 | 비고 |
| --- | --- | --- |
| **MVP** | 수동 큐레이션 20~50건 (JSON) + 내 스택 태그 매칭 + 마감일 지난 항목 자동 숨김 + 저장(기존 북마크 재활용) | 백엔드 수집기 없이 시작 가능. 발표 시연에 충분 |
| 2차 | 온통청년 · 정부지원일자리 API를 하루 1회 수집해 개발 관련만 걸러 추가 | 공공데이터 이용 조건(출처 표시 등) 지키기 |
| 3차 | 기업이 직접 등록 (기획서 6장 수익화의 "기업 챌린지"와 연결) | 사용자 규모가 생긴 뒤 |

**공통 원칙**

- 지원은 **원래 사이트에서** 한다. Pofol은 원문 링크로 보낸다 (공고 내용을 복제해 두지 않는다).
- 출처 · 마감일 · 등록일을 항상 표시한다.
- 추천 이유를 보여준다 — "내 레포에 Spring 3개 → 백엔드 과정 추천" (규칙 매칭, AI 판단 아님).

### 3.5 핵심 흐름에 어떻게 붙나

```
레포 분석 → 피드백 → 트렌드
     │
     └─→ 기회 피드: "내 스택에 맞는 프로젝트 · 교육 · 공고"
              └─→ 지원 전 "이 공고를 위한 레포 점검" (대표 프로젝트 · README 확인)
```

## 4. 바뀐 서비스 구조

| 구분 | 기능 | 기존 계획 대비 |
| --- | --- | --- |
| **메인** | 레포 분석 · 피드백 · 트렌드 | 그대로 |
| **메인 (신규)** | 기회 피드 (기업 · 정부 프로젝트, 교육, 공고) | 추가 |
| 부가 | README 초안, 이력서, 프로젝트 카드, 발표자료 | 그대로 |
| **메인 (신규)** | 공개 포트폴리오 링크 (지원서 제출용) | 기존 `/profile/[id]` 다듬기 |
| 제외 | 게시판 · 피드 · 사람끼리 피드백 | 메인 메뉴에서 뺌, 데이터는 유지 |
| 재활용 | 북마크 → **기회 저장** | 용도 변경 |
| **삭제** | 팀원 모집 (지원 · 지원자 관리 포함) | 기존 "대기"에서 삭제로 |

성장 단계(기획서 10.2)의 3단계에서 "팀원 모집"을 빼고 "기업 직접 등록 · 학과 쇼케이스"로 바꾼다.
