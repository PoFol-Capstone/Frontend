## 1. 한 줄 정의

> **취업 전에, 내 GitHub 레포를 혼자서도 점검할 수 있게 돕는 곳**

평가해 주는 곳이 아니라 **스스로 점검하고 고치는 걸 보조하는 곳**이다.

## 2. 왜 바꿨나 — 판단의 흐름

| 순서 | 판단 | 이유 |
| --- | --- | --- |
| 1 | 커뮤니티 중심을 버린다 | 피드백 · 북마크 · 모집 모두 "사용자가 많다"는 전제가 필요. 빈 피드는 다시 오지 않을 이유가 된다 (콜드 스타트). 학생끼리의 피드백은 질이 낮다 |
| 2 | 레포 기반 정리를 중심으로 올린다 | 커뮤니티 기능 중 유일하게 **혼자 써도 가치가 있던 기능** (게시글 작성 때 레포 → AI 정리) |
| 3 | "본인 레포 피드백 사이트"로 재정의 | 사용자가 이 사이트를 쓸 수밖에 없는 이유를 먼저 만든다 |
| 4 | AI는 "보조"로 둔다 | "AI가 무슨 근거로 판단하냐"에 답할 근거가 약하다. LLM 판정은 규칙 확인에는 강하고 주관적 판단에는 약하다는 연구 결과, 개발자도 AI 정확도를 불신(46%)하는 쪽이 신뢰(33%)보다 많다 |
| 5 | 팀원 모집을 삭제한다 | 처음 온 사람은 그 프로젝트가 도움이 될지 신뢰할 근거가 없다. 완주율이 낮다. 기업 · 정부 프로젝트가 더 나은 대안 |
| 6 | 게시판 · 피드를 메인에서 뺀다 | "올려서 뭐하지?" — 올리는 사람이 얻는 게 없다. 사람들이 공개하는 진짜 이유는 **지원서에 붙일 링크가 필요해서** |
| 7 | 기업 · 정부 기회를 연결한다 | 주최자가 분명해 신뢰가 있고, 계속 새로 올라와 재방문 이유가 되며, 외부 데이터라 콜드 스타트가 없다 |

**모든 판단의 공통 기준:** 다른 사용자가 한 명도 없어도 가치가 생기는가?

## 3. 타겟과 문제

**타겟:** 지원서에 GitHub를 내야 하는 개발자 지망생 (대학생 1~4학년, 부트캠프 수료생)

**문제:** 레포 점검은 결국 혼자 해야 한다.

| 지금 방법 | 한계 |
| --- | --- |
| 유료 멘토링 · 첨삭 | 시간당 약 5만 원, 건당 과금 — 반복하기 어렵다 |
| 현업 개발자에게 들은 말, 선배 레포 | 일반론이거나 내 레포에 맞지 않는다 |
| 블로그 · 유튜브 · ChatGPT | 적용과 확인은 혼자, 근거가 안 보인다 |

**상황 (조사 수치):**

| 지표 | 수치 | 출처 |
| --- | --- | --- |
| 신입 채용 시 '직무 관련 경험'을 최우선으로 보는 기업 | 81.6% (3년 새 58.4% → 81.6%) | 경총 2025 |
| IT · 통신 대기업 신입 공고 | 전년 대비 67% 감소 | 진학사 캐치 |
| 전체 대기업 신입 공고 | 43% 감소 | 같은 분석 |
| 미취업 청년의 최대 애로 | 약 80%가 "업무 경험 부족" | 경총 2025.10 |

> 10/25 기획서의 "82% 경력직만 · 신입 2.6%", "85% 경력 있는 신입", "사이드 프로젝트 26.2%"는 원 출처를 확인하지 못해 **교체했다.**

## 4. 시장 · 경쟁 판단

| 판단 | 근거 |
| --- | --- |
| 비슷한 서비스는 있지만 **대상이 다르다** | GitRoll · CodersRank 등은 결국 **채용 담당자가 지원자를 거르는 도구**로 갔다. 나머지는 대부분 학생 · 해커톤 프로젝트 |
| 국내 운영 중인 취준생용 레포 점검 서비스는 **확인되지 않았다** | 국내 사례는 부트캠프 결과물(Giterview) 수준 |
| 차별점 | "평가받는 도구"가 아니라 "**스스로 고치는 도구**", 한국어 · 국내 채용 맥락 |

**왜 지금까지 자리 잡지 못했나 (분석 · 추정):**
좋은 레포의 기준이 없다 / 돈을 내는 쪽이 기업이다 / 한 번 쓰면 끝난다 / LLM 비용 장벽이 최근에야 낮아졌다 / 해외 도구엔 국내 맥락이 없다 / AI 신뢰 문제.
→ Pofol은 각각 규칙 기반 사실, 학생 무료, 재점검 루프, 요약 데이터만 전송, 한국어 · 국내 지표, 보조 포지션으로 대응한다.

**수요:** 직접적인 정량 자료는 없다. 간접 지표(경험 증명 요구 증가, 신입 경쟁 심화, 유료 첨삭 시장 존재)로 흐름만 확인했다. → **교내 설문과 1월 사용자 테스트로 직접 검증한다.**

## 5. 서비스 구조 (확정)

| 구분 | 기능 | 상태 |
| --- | --- | --- |
| **핵심 ①** | 레포 분석 — 사실 데이터 (AI 없음) | 1차 구현 있음 |
| **핵심 ②** | 피드백 — 할 일 목록, 규칙 사실(✅)과 AI 제안(🤖) 구분 | 1차 구현 있음, 개선 예정 |
| **핵심 ③** | 트렌드 분석 — 내 스택 vs 국내 · 해외 시장 지표 | 신규 |
| **메인 (신규)** | 기회 피드 — 기업 · 정부 프로젝트, 교육, 공고 (내 스택 매칭) | 신규 |
| **메인 (다듬기)** | 공개 포트폴리오 링크 — 지원서 제출용 | 기존 `/profile/[id]` 다듬기 |
| 부가 | README 초안, AI 이력서, 프로젝트 카드, 발표자료 | 구현됨 · 진행 중 |
| 재활용 | 북마크 → 기회 저장 | 용도 변경 |
| 메인에서 제외 | 게시판 · 피드 · 댓글 · 사람끼리 피드백 | 데이터 유지, 사용자 생기면 재판단 |
| **삭제** | 팀원 모집 (지원 · 지원자 관리 포함) | 1단계 숨김 → 2단계 코드 삭제 |

**핵심 흐름:**

```
GitHub 연동 → ① 레포 분석 → ② 피드백(할 일 목록) + ③ 트렌드 비교
   → GitHub에서 수정 → 다시 분석 → 체크 채워짐 ("지난번보다 3개 해결")
   → 공개 포트폴리오 링크로 지원서 제출
   → 기회 피드: 내 스택에 맞는 기업 · 정부 프로젝트 · 교육 → 지원 전 레포 점검
```

## 6. 핵심 기능별 판단

### 6.1 레포 분석 · 피드백

| 판단 | 내용 |
| --- | --- |
| 점수를 보여주지 않는다 | 해결하면 체크되는 할 일 목록 |
| 판정은 규칙, 문장은 AI | 규칙으로 확인 가능한 것은 AI 없이. AI는 정리 · 문장화 · 제안만 |
| 이미 모은 데이터를 더 쓴다 | 점검 결과가 AI 입력에 없음 → 넣는다. README는 2,000자 저장하는데 300자만 사용 → 제목 목록 + 앞부분으로 확대 |
| 추가 비용 없는 새 규칙 | 이미 받는 루트 파일 목록으로: `.env` 커밋(보안), CI 없음, README 실행 방법 없음 등 |
| 코드가 계산해서 넘긴다 | 기술 변화(시기별 언어), 프레임워크, 팀 레포 본인 기여 비중 — AI가 추측하지 않게 |

### 6.2 Organization 레포 (버그 수준)

| 항목 | 내용 |
| --- | --- |
| 원인 | 레포 목록 요청이 `affiliation=owner` → 본인 소유만. Organization 레포와 **팀원 계정의 협업 레포도 빠짐** (`GitHubCollector.java:67`, `GitHubService.java:58`) |
| 권한 문제는 아님 | Pofol은 공개 레포만 보고, Organization 접근 제한은 비공개 자원만 막는다 (GitHub 문서) |
| 같이 해야 할 것 | 본인이 커밋한 레포만 남기기 (학교 Organization 레포 수백 개 유입 방지), 소유 구분(OWNER/ORG/COLLABORATOR), 계정 점검은 본인 레포만, 팀 레포 피드백은 "팀에 제안" 문구 |
| 확인 필요 | 실제 계정으로 Organization 공개 레포가 목록에 나오는지 |

### 6.3 트렌드 분석

| 판단 | 내용 |
| --- | --- |
| 수치는 코드가 넣는다 | AI는 비교 요약 문장만 |
| 국내 · 해외를 나눈다 | 국내는 JS · Java 강세, 해외는 TypeScript 1위 (Octoverse 2025) — 차이 자체가 유용한 정보 |
| 출처 없는 수치 금지 | 출처 · 발표일 · 확인일이 없으면 테스트에서 실패하게 |

### 6.4 기회 피드

| 판단 | 내용 |
| --- | --- |
| 첫 버전은 수동 등록 | 기업 교육 · 해커톤 · 일경험 20~50건을 JSON으로. 수집 서버 없이 시작 |
| 2차에 공공 API | 온통청년 청년정책 API, 정부지원일자리 모집정보 API (무료, 활용신청 필요). 개발 직군 비중이 낮을 수 있어 실제 데이터 확인 먼저 |
| 민간 사이트 크롤링 금지 | 사람인 · 잡코리아 등은 이용 조건 확인 전까지 하지 않음 |
| 지원은 원래 사이트에서 | 원문 링크로 보낸다. 마감 지난 항목은 자동 숨김 |
| 추천 이유 표시 | "내 레포에 Spring 3개 → 백엔드 과정" (규칙 매칭) |

### 6.5 공개 포트폴리오 링크

| 판단 | 내용 |
| --- | --- |
| 피드 대신 링크 | 공개하는 이유 = 본인 지원서. 보는 사람 = 채용 담당자. 다른 사용자가 없어도 가치 있음 |
| 새로 만들지 않음 | 기존 `/profile/[id]`(공개 설정 항목만 노출)를 지원서용으로 다듬는다 |

## 7. AI · 프롬프트 방향

| 항목 | 판단 |
| --- | --- |
| 톤 | **분석 AI** — 관찰 → 근거 → 제안. 감정 · 점수 · 단정 없이 존댓말 평서문. 데이터가 부족하면 "판단할 데이터가 부족합니다" |
| 근거 표시 | **사실 ID 방식** — 코드가 사실 목록(F1, F2…)을 만들어 넘기고, AI는 번호만 단다. 화면은 코드가 만든 원문을 보여준다 → 근거가 왜곡될 수 없음 |
| 할루시네이션 방지 | 4겹: ① 사실 목록만 입력, 지시(system)와 레포 데이터(user) 분리 ② 출력 구조 강제 ③ 생성 후 코드 검증 — 없는 번호 · 입력에 없는 숫자 · 기술명이 나오면 그 항목 버림 ④ 실제 레포로 고정 평가 세트 |
| 출력 형식 | **Structured Outputs (`json_schema`, strict)** — 기존 `openai` 패키지와 `gpt-4o-mini`로 가능, 새 의존성 없음 |
| 확신도 | AI가 스스로 매긴 확신도는 쓰지 않는다. 근거가 규칙 사실인지로 코드가 판단 |
| 기존 라우트 정리 | `github-direction` · `profile-readme` · `resume`은 지시와 데이터가 한 메시지에 섞여 있음 → `project-card`처럼 분리 |

## 8. 지표 — 서비스 성과와 갱신

### 8.1 서비스 성과 지표

| 지표 | 정의 |
| --- | --- |
| **재점검 비율** (핵심) | 첫 분석 후 30일 안에 다시 분석한 사용자 ÷ 분석한 사용자 |
| **해결률** | 다시 분석했을 때 사라진 점검 항목 ÷ 이전 점검 항목 (무시 항목 제외) |
| 항목별 해결률 | 어떤 피드백이 쉽게 실행되는지 |
| 결과물 생성률 | 분석 사용자 중 README · 이력서 · 카드 · 공개 링크를 만든 비율 |

- **지금은 측정이 불가능하다.** 분석 결과를 유저당 1건만 두고 덮어쓰기 때문. → **분석 이력 테이블 1개 추가** (분석 시각 + 남은 점검 항목). 사용자 화면의 "지난번보다 N개 해결"도 이걸로 만든다.
- 공개된 벤치마크가 없어서 1월 사용자 테스트에서 첫 기준값을 잰다.

### 8.2 트렌드 지표 갱신

| 종류 | 방법 | 주기 |
| --- | --- | --- |
| 외부 조사 (Stack Overflow, Octoverse, JetBrains, 원티드, 경총 · 캐치) | 사람이 원문 확인 후 JSON 수정, 갱신 달력 운영 | 연 1회 (발표 시기 맞춤) |
| 자동 수집 (선택) | GitHub 검색 API로 언어별 신규 레포 수 | 월 1회 |
| Pofol 내부 | 사용자 분석 집계 | 주 1회, **사용자 30명 이상일 때만 표시** |

## 12. 확인이 필요한 것 (근거가 약한 부분)

- Stack Overflow 언어 · DB 수치, 원티드 리포트는 기사 · 블로그로 확인한 2차 자료 — 발표 전 원문 확인
- 잡코리아 "포트폴리오 필수 51.8%"는 2021년 무렵 자료
- "왜 이런 서비스가 없었나"는 조사 사실에 기반한 **추정**
- Organization 공개 레포가 실제로 목록에 나오는지 — 실제 계정으로 확인
- 정부지원일자리 API에 개발 직군 공고가 얼마나 있는지 — 활용신청 후 확인
- 수요(실제로 몇 명이 쓸지) — 아직 검증 안 됨
