## 1. 한 줄 정의

> **취업 전에, 내 GitHub 레포를 혼자서도 점검할 수 있게 돕는 곳**

개발자 취준생은 지원서에 GitHub 레포를 낸다. 그런데 그 레포가 "보여줄 만한 상태"인지 확인할 방법이 마땅치 않다.
Pofol은 그 점검을 **보조**한다. 대신 판단해주는 게 아니라, 스스로 점검할 때 빠뜨리기 쉬운 것을 짚어주고 시장 흐름과 비교할 자료를 준다.

## 2. 배경 — 기존 커뮤니티 방식과 그 문제

### 2.1 처음 기획 (커뮤니티형)

처음 Pofol은 학생들이 프로젝트를 **게시글로 올리고**, 서로 피드백 · 북마크 · 팀원 모집을 하는 커뮤니티였다.

| 기능 | 의도 |
| --- | --- |
| 프로젝트 게시글 | 내 프로젝트를 소개하고 보여주기 |
| 댓글 · 피드백 | 다른 사람에게 의견 받기 |
| 북마크 · 팔로우 | 좋은 프로젝트 모아보기 |
| 팀원 모집 | 프로젝트 팀 꾸리기 |

### 2.2 문제점 분석

**① 커뮤니티가 형성되지 않으면 모든 기능이 쓸모없어진다**

- 피드백은 피드백을 줄 사람이 있어야 성립한다. 글을 올려도 댓글이 없으면 올린 사람이 얻는 게 없다.
- 북마크는 볼 만한 글이 쌓여야, 팀원 모집은 지원할 사람이 있어야 의미가 있다.
- 즉 모든 핵심 기능이 **"사용자가 이미 많다"는 전제** 위에 있다. 초기 서비스에는 그 전제가 없다.

**② 사용자가 들어올 이유가 없다 (콜드 스타트)**

- 첫 방문자는 빈 피드를 본다 → 볼 게 없으니 다시 오지 않는다 → 글이 더 안 쌓인다.
- 글을 쓰는 사람도 "누가 봐줄까"를 먼저 생각한다. 보는 사람이 없으면 쓰지 않는다.
- 이미 velog · 티스토리 · 링커리어 · 각종 오픈채팅방이 같은 역할을 하고 있어, 비어 있는 새 커뮤니티를 고를 이유가 약하다.

**③ 피드백의 질을 보장할 수 없다**

- 커뮤니티 피드백은 대부분 같은 학생끼리다. "좋네요", "고생하셨어요" 수준에 그치기 쉽다.
- 취업 관점에서 레포를 볼 줄 아는 사람(현업 · 채용 담당)이 들어올 유인이 없다.

**④ 그런데 혼자서도 가치가 있는 기능이 하나 있었다**

- 게시글 작성 시 **GitHub 레포를 연결하면 AI가 내용을 정리해주는 기능**(`api/ai/summarize`, `api/github/repo-info`).
- 이 기능은 다른 사용자가 한 명도 없어도 쓸모가 있다. 내 레포를 넣으면 바로 결과가 나온다.
- 커뮤니티 기능 중 유일하게 **혼자 써도 가치가 생기는 기능**이었다.

### 2.3 결론 — 방향 전환

| | 기존 (커뮤니티형) | 변경 (개인화형) |
| --- | --- | --- |
| 핵심 가치 | 다른 사람과의 교류 | **내 레포에 대한 피드백** |
| 가치가 생기는 조건 | 사용자가 많아야 함 | 사용자 1명이어도 됨 |
| 첫 방문 경험 | 빈 피드 | GitHub 연동 → 바로 내 레포 점검 결과 |
| 재방문 이유 | 새 글 · 댓글 알림 | 고친 뒤 다시 점검 → 체크리스트가 채워짐, 트렌드 지표 갱신 |
| 커뮤니티 기능 | 메인 | **보류 · 대기** (사용자가 쌓인 뒤 활성화) |

> 게시글 작성 때 쓰던 **레포 기반 내용 정리**를 서비스의 중심으로 끌어올리고,
> **"본인 레포 피드백 사이트"** 로 재정의한다.

지금 당장의 목표는 커뮤니티 활성화가 아니라 **사용자가 이 사이트를 쓸 수밖에 없는 이유를 만드는 것**이다.

## 4. 문제 정의

### 4.1 상황 — 신입 문은 좁아지고, "경험의 증명"이 중요해졌다

| 지표 | 수치 | 출처 |
| --- | --- | --- |
| 신입 채용 시 가장 중요한 평가 요소로 **'직무 관련 업무 경험'** 을 꼽은 기업 | **81.6%** (2023년 58.4% → 2024년 74.6% → 2025년 81.6%) | 경총 「2025 신규채용 실태조사」, 100인 이상 기업 500곳 [S1][S2] |
| 올해 신규채용 계획이 있는 기업 | 60.8% (2022년 72.0% 이후 최저) | 같은 조사 [S1] |
| 대기업 정규직 **신입** 채용 공고 수 | 전년 대비 **43% 감소** (3,741건 → 2,145건, 2024·2025년 1~11월 비교) | 진학사 캐치 분석 [S3][S4] |
| 그중 **IT·통신** 업종 신입 공고 | **67% 감소** (899건 → 293건), 전 업종 중 최대 | 같은 분석 [S3][S4] |
| 대졸 신규 입사자 중 이미 경력이 있던 "중고 신입" | 28.1% (전년 대비 +2.3%p) | 한경협, 매출 상위 500대 기업 [S5] |
| 미취업 청년이 꼽은 취업 준비 최대 애로 | 약 80%가 "업무 경험 · 경력개발 기회 부족" | 경총, 2025.10 [S6][S7] |

**해석:** 개발 직군 신입 자리는 크게 줄었고, 기업은 "해본 적 있는가"를 가장 먼저 본다.
학생이 실무 경험 대신 내밀 수 있는 가장 직접적인 증거가 **GitHub 레포**다. 그만큼 레포의 상태가 중요해졌다.

> 채용 담당자가 GitHub를 실제로 얼마나 보는지에 대한 **국내 정량 설문은 찾지 못했다.** 발표에서 이 부분은
> "직무 경험 최우선(81.6%) → 학생에게 경험의 증거는 프로젝트 · 레포"라는 논리로 연결하고, 단정적 수치는 쓰지 않는다.

### 4.2 지금 점검하는 방법과 한계

| 방법 | 한계 |
| --- | --- |
| 유료 멘토링 · 컨설팅 | 비싸다. 포트폴리오 컨설팅 평균 **시간당 약 5만 원**(숨고, 개발 직군 외 포함), 크몽 개발자 첨삭은 프로젝트 3개 초과 시 **1개당 2만 원 추가** 같은 건당 과금 [S8][S9]. 여러 번 받기 어렵다 |
| 현업 개발자에게 들은 말 | 한두 마디로 끝나고, 내 레포에 맞춘 얘기가 아니다 |
| 선배 · 잘된 사람 레포 참고 | 무엇이 좋은지 스스로 해석해야 하고, 내 레포와 비교가 안 된다 |
| 블로그 · 유튜브 가이드 | 일반론이다. 결국 적용과 확인은 혼자 해야 한다 |
| ChatGPT 등 범용 AI | 레포를 직접 붙여넣어야 하고, 매번 처음부터 설명해야 하며, 답의 근거가 보이지 않는다 |

**공통점: 결국 점검은 본인이 스스로 해야 한다.** 기준은 흩어져 있고, 내 레포에 대고 확인해주는 곳은 없다.

### 4.3 Pofol이 푸는 것

- 흩어진 기준을 모아 **내 레포에 직접 대어 본다.** (레포 분석)
- 빠진 것을 **할 일 목록**으로 보여주고, 고치면 체크가 채워진다. (피드백)
- 내 기술 스택을 **시장 지표와 나란히** 보여준다. (트렌드 분석)

## 5. 시장 · 경쟁 서비스 조사

### 5.1 비슷한 기존 서비스

조사 결과 "GitHub를 분석해 개발자를 평가하는" 서비스는 이미 있다. 다만 **누구를 위한 서비스인가**가 다르다.

| 서비스 | 형태 | 대상 | 하는 일 | 상태 · 한계 |
| --- | --- | --- | --- | --- |
| **GitRoll** (미국) | 상용 | **채용 담당자** 중심 | 공개 GitHub 코드를 800여 개 규칙으로 스캔해 보안 · 신뢰성 · 유지보수성 등 점수화 [S10][S11] | 이후 채용 플랫폼(개발자 프로필 수집, AI 리크루터)으로 확장. 유료 플랜 월 $69부터라는 제3자 정보 있음(미확인) |
| **CodersRank** | 상용 | 개발자 + 채용 담당자 | GitHub 등 계정을 연결해 개발자 프로필 · 랭킹 생성 [S12] | 채용 매칭이 목적. 레포 개선 피드백은 아님 |
| **Sourcerer** | 오픈소스 | 개발자 | git 기록으로 시각적 프로필 생성 [S13] | 2020년 9월 이후 개발 멈춤으로 보임(마지막 push 기준, 종료 공지는 미확인) |
| GitHub Portfolio Analyzer, GitSignal AI, AI Github Auditor, Dev-Score 등 | 개인 · 해커톤 프로젝트 | 취준생 | 프로필 점수, 개선 팁, 직무 추천 [S14] | 대부분 학생 · 취미 프로젝트. 유지보수 불확실, 영어권 |
| **Giterview** (국내) | 부트캠프 프로젝트 | 취준생 | GitHub 정보로 이력서 · AI 면접 [S15] | 2023년 부트캠프 결과물, 운영 서비스 아님 |
| github-readme-stats 등 | 오픈소스 위젯 | 개발자 | 언어 비중 · 통계 카드 표시 | 보여주기만 하고 점검 · 피드백은 없음 |
| 크몽 · 숨고 첨삭 | 사람 서비스 | 취준생 | 포트폴리오 · 이력서 첨삭 [S8][S9] | 비싸고 1회성, GitHub 레포 자체를 보는 서비스는 드묾 |

**국내에서 운영 중인, 취준생 대상 GitHub 레포 점검 서비스는 이번 조사에서 확인되지 않았다.**

### 5.2 차별점

| | 유료 첨삭 | 범용 AI 챗봇 | GitRoll 등 해외 분석 도구 | **Pofol** |
| --- | --- | --- | --- | --- |
| 주 사용자 | 취준생 | 누구나 | **채용 담당자** | **취준생 본인** |
| 결과의 목적 | 서류 다듬기 | 질문 답변 | 후보자 선별 (점수) | **본인이 고칠 할 일 목록** |
| 비용 | 시간당 ~5만 원 / 건당 과금 | 무료~저가 | 기업 유료 | 무료 (AI 횟수 제한) |
| 내 레포 연동 | 사람이 직접 봄 | 직접 붙여넣기 | 자동 | **자동** |
| 반복 점검 | 추가 비용 | 매번 처음부터 | 기업이 조회 | **다시 분석 → 진행 상황 유지** |
| 근거 표시 | 사람에 따라 | 거의 없음 | 점수 + 규칙 | **사실(규칙) / AI 제안 구분** |
| 국내 맥락 (한국어, 국내 채용 흐름) | O | 일부 | X | **O** |

핵심 차이는 **"평가받는 도구"가 아니라 "스스로 고치는 도구"** 라는 점이다. 해외 도구는 채용 담당자가 지원자를 거르는 쪽으로 갔고,
Pofol은 지원자가 제출 전에 스스로 준비하는 쪽을 맡는다.

## 6. 왜 이런 서비스가 (국내에) 자리 잡지 못했나

조사한 사실을 바탕으로 한 **분석(추정)** 이다. 각 항목마다 Pofol의 대응을 붙였다.

| 원인 | 근거 | Pofol의 대응 |
| --- | --- | --- |
| **① "좋은 레포"의 기준이 없다** | 연구에 따르면 LLM 판정은 규칙 확인처럼 정답이 있는 작업에서는 사람과 잘 맞지만(정확도 0.85, κ 0.71), 주관적인 품질 판단에서는 약하고, 틀리는 곳도 사람끼리 의견이 갈리는 곳에 몰린다 [S16][S17][S18] | 점수 대신 **규칙으로 확인 가능한 항목**을 중심에 두고, 주관적 판단은 "제안"으로만 보여준다 |
| **② 돈을 내는 쪽은 기업이다** | GitRoll · CodersRank 모두 결국 채용 담당자 쪽 상품으로 갔다 [S10][S12]. 취준생은 지불 의사가 낮다 | 학생 기능은 무료, 수익은 사용자가 쌓인 뒤 학교 · 기업 쪽에서 (10/25 기획서 6장) |
| **③ 한 번 쓰면 끝난다** | 개인용 프로필 도구는 개발이 멈춘 사례가 많다(Sourcerer 2020년 이후 업데이트 없음 [S13], 해커톤 프로젝트 다수) | **재점검 루프**(고치면 체크), **트렌드 지표 갱신**으로 다시 올 이유를 만든다 |
| **④ 비용 · 기술 장벽이 최근에야 낮아졌다** | 코드를 읽고 문장으로 피드백하는 일은 저가 LLM이 나오기 전엔 비쌌다 | 코드 원문 대신 메타데이터 · README 일부만 보내 1회 수 원 수준으로 (10/25 기획서 4장) |
| **⑤ 국내 맥락이 빠져 있다** | 해외 도구는 영어 · 해외 채용 기준이다 | 한국어 피드백, 국내 채용 흐름 · 국내 개발자 설문을 트렌드 지표에 반영 |
| **⑥ 신뢰 문제** | Stack Overflow 2025: AI 정확도를 **불신 46% > 신뢰 33%**, "거의 맞지만 틀린 답"이 가장 큰 불만(66%) [S19][S20] | "보조" 포지션, 근거 표시, 최종 판단은 사용자 (8장) |

**직접 수요(이런 서비스를 원하는 사람 수)를 보여주는 정량 자료는 찾지 못했다.** 아래는 간접 지표다.

| 간접 지표 | 내용 | 출처 | 주의 |
| --- | --- | --- | --- |
| 경험 증명 요구 증가 | 직무 경험 최우선 81.6%, 3년 새 +23%p | [S1][S2] | 기업 측 조사 |
| 신입 경쟁 심화 | IT·통신 대기업 신입 공고 67% 감소 | [S3][S4] | 대기업 · 캐치 게재 공고 기준 |

다만 실제로 몇 명이 쓸지는 **직접 검증이 필요하다.**

**검증 계획 (제안):**

- [ ] 교내 컴공 · SW 계열 학생 대상 설문 (GitHub 제출 경험, 점검 방법, 멘토링 비용 지출 경험, 사용 의향)
- [ ] 1월 통합 QA 때 실제 학생 5~10명 사용자 테스트 → 재점검 비율 측정
- [ ] 정확한 모수가 필요하면 교육통계서비스(KESS) 학과별 졸업자, 고용24 K-디지털 트레이닝 훈련생 통계 확인

## 8. 포지셔닝 — 왜 "보조"인가

### 8.1 AI가 판단하지 않는다

"AI가 무슨 근거로 이 레포가 잘됐다 · 못됐다고 판단하느냐?"는 질문에 우리는 확실한 답을 갖고 있지 않다.

- 좋은 레포의 기준은 회사 · 직무 · 면접관마다 다르다.
- LLM 판정은 정답이 있는 확인 작업에서는 쓸 만하지만, 주관적인 품질 판단에서는 근거가 약하다 [S16][S17].
- 개발자 스스로도 AI 결과를 신뢰하지 않는 쪽이 더 많다 (불신 46% vs 신뢰 33%) [S19].

그래서 Pofol은 **평가자가 아니라 보조 도구**로 자리 잡는다.

### 8.2 보조 도구로서의 원칙

| 원칙 | 내용 |
| --- | --- |
| **점수를 매기지 않는다** | "72점" 대신 해결하면 체크되는 할 일 목록으로 보여준다 |
| **사실과 의견을 나눈다** | 규칙으로 확인한 사실(README 없음, 커밋 2개)과 AI의 제안을 화면에서 구분한다 |
| **근거를 보여준다** | 왜 이 항목이 떴는지, 어떤 데이터를 봤는지, 지표는 출처와 기준 시점을 함께 표시한다 |
| **확인 가능한 것부터** | 규칙으로 판정 가능한 항목은 AI 없이 처리한다. AI는 정리 · 문장화 · 제안에만 쓴다 |
| **최종 판단은 사용자** | 무시 토글, 편집 가능한 초안 — 결정은 언제나 본인이 한다 |

> 정리: Pofol은 "당신의 레포는 좋다/나쁘다"라고 말하지 않는다.
> "이런 것들을 확인해 보세요, 이건 이렇게 보완할 수 있습니다, 시장은 지금 이렇습니다"라고 말한다.

## 9. 필수 기능 (확정)

"쓸 수밖에 없는 이유"가 되는 기능은 세 가지다. 나머지(README 초안, 이력서, 발표자료 등)는 이 셋의 결과물을 활용하는 부가 기능이다.

```
① 레포 분석 ──→ ② 피드백 (할 일 목록) ──→ 고친 뒤 다시 분석
       │
       └──→ ③ 트렌드 분석 (내 스택 vs 시장)
```

### 9.1 ① 레포 분석

내 GitHub를 연동하면 레포를 자동으로 읽어 **사실 데이터**를 만든다. 이 단계에는 AI가 없다.

| 분석 항목 | 내용 | 현재 상태 |
| --- | --- | --- |
| 레포 개요 | 레포 수(직접 / 포크), 스타, 마지막 push, 최근 90일 활동 | 1차 구현 (`GitHubTab`) |
| 언어 비중 | 레포별 `languages` 합산, 상위 5개 + 기타 | 1차 구현 |
| 프레임워크 · 라이브러리 감지 | `package.json`, `build.gradle`, `pom.xml`, `requirements.txt` 등 의존성 파일에서 추출 | **일부 있음** — 게시글 작성용 단일 레포 감지(`lib/github.ts` + 백엔드 `GitHubService.CONTENT_FILES`). 전체 분석에 연결하는 건 신규 (트렌드 분석의 입력) |
| 레포 구조 | README · 테스트 폴더 · 배포 링크 · 설명/토픽 유무 | 1차 구현 |
| 커밋 이력 | 커밋 수, 기간, 메시지 패턴 | 1차 구현 |
| 레포 컨텍스트 | 파일 트리, 핵심 파일 요약 (프로젝트 정리 카드용) | 2차 진행 중 (`project-card`) |

### 9.2 ② 피드백

분석 결과를 **할 일 목록**으로 바꾼다. 피드백은 두 층으로 나눠 화면에서 구분한다.

| 층 | 만드는 방법 | 예시 | 표시 |
| --- | --- | --- | --- |
| **규칙 피드백 (사실)** | 코드 규칙. AI 없음 | "README가 없습니다", "최근 커밋 10개 중 8개가 'update'입니다" | ✅ 확인됨 |
| **AI 제안 (의견)** | LLM이 분석 데이터를 근거로 문장 생성 | "이 레포는 인증 흐름을 README 첫 화면에 보여주면 백엔드 역량이 더 잘 드러납니다" | 🤖 AI 제안 + 참고한 데이터 표시 |

- 고친 뒤 [다시 분석]하면 체크가 채워진다 → **재방문 루프**.
- 항목별 "무시" 토글 (연습용 레포 등).
- 레포 단위 피드백 + 전체 프로필 단위 피드백(대표 프로젝트, 방향성).
- AI 제안의 범위 · 문장 규칙 · 근거 인용 방식은 **다음 세션(프롬프트 설계)에서 정한다.**

### 9.3 ③ 트렌드 분석 (언어 · 프레임워크 · 개발 시장)

내 기술 스택을 **시장 지표와 나란히** 보여준다. "무엇을 더 공부하라"고 정해주지 않고, 비교 자료를 준다.

**보여줄 지표**

| 영역 | 지표 | 데이터 출처 (후보) |
| --- | --- | --- |
| 언어 | 내 언어 비중 vs 국내 개발자 사용 언어 vs 전 세계 사용 · 성장률 | 원티드 개발자 리포트, Stack Overflow Survey, GitHub Octoverse |
| 프레임워크 · 도구 | 내 프레임워크 vs 많이 쓰는 · 성장 중인 프레임워크, DB, 인프라 도구 | Stack Overflow Survey, JetBrains Developer Ecosystem |
| 개발 시장 | 신입 채용 흐름, 직군 · 업종별 공고 변화, 채용 공고에 자주 나오는 기술 | 경총 · 캐치 · 한경협 조사, (검토) 채용 공고 기술스택 집계 |
| Pofol 내부 (2단계 이후) | Pofol 사용자들의 언어 · 프레임워크 분포, 같은 희망 직무 사용자 비교 | Pofol DB 집계 — 사용자가 적을 땐 표시하지 않음 |

**현재 확인한 시장 지표 (초기 데이터 예시)**

| 지표 | 수치 | 출처 |
| --- | --- | --- |
| GitHub 최다 사용 언어 | **TypeScript**가 2025년 8월 Python · JavaScript를 넘어 1위, 기여자 전년 대비 +66% | GitHub Octoverse 2025 [S24][S25] |
| GitHub 신규 개발자 | 지난 1년 3,600만 명 이상 (초당 1명 이상) | 같은 자료 [S24] |
| 전 세계 개발자 사용 언어 | JavaScript 약 66%, HTML/CSS 61.9%, SQL 58.6%, Python 57.9% (전년 +7%p) | Stack Overflow 2025 (2차 보도 기준, 원문 확인 필요) [S26] |
| 도구 · DB | Docker 71.1%, PostgreSQL 55.6%, MySQL 40.5%, Redis 28% | 같은 자료 (2차 보도) [S26] |
| 유망 언어 | TypeScript · Rust · Go (Language Promise Index) | JetBrains 2025, 24,534명 [S27] |
| **국내** 개발자 주 사용 언어 | JavaScript 49.1%, Java 37.1%, TypeScript 23.6%, Python 18.7%, Kotlin 8.4% | 원티드 개발자 리포트, 508명 [S28] |
| 국내 개발 직군 공고 비중 | IT 산업 22.4%, 개발 · IT 직무 19.9%로 1위 (2025 상반기) | 비즈니스피플 [S29] |

> 국내(Java · Spring 강세)와 해외(TypeScript · Python 강세)의 흐름이 다르다는 것 자체가 학생에게 유용한 정보다.
> 트렌드 화면은 **국내 · 해외를 나눠** 보여준다.

**설계 원칙**

- 지표마다 **출처 · 조사 시점 · 표본**을 함께 표시한다. 출처 없는 수치는 넣지 않는다.
- 외부 지표는 연 1~2회 발표되므로 **수동 갱신 데이터(JSON)** 로 시작한다. 자동 수집은 필요해지면 검토.
- 채용 공고 크롤링은 각 사이트 약관 확인 전까지 하지 않는다.
- AI는 "내 스택과 지표를 비교한 요약 문장"에만 쓴다. 수치 자체를 AI가 만들지 않는다.

### 9.4 필수가 아닌 것 (부가 · 대기)

| 기능 | 분류 | 이유 |
| --- | --- | --- |
| 프로필 README 초안, AI 이력서, 프로젝트 정리 카드 | 부가 (유지) | 분석 · 피드백 결과를 활용하는 결과물. 구현 완료 · 진행 중 |
| 발표자료 뷰어, 프로필 사진 | 부가 (유지) | 이미 구현됨 |
| 피드 · 댓글 · 팔로우 · 북마크 | 대기 | 10장 성장 단계에서 활성화 |
| 팀원 모집 | **삭제 검토 중** | 신뢰 · 완주율 문제, 기업 · 정부 프로젝트가 더 나은 대안 (`2026-11-06-pivot-review-community.md`) |

## 10. 서비스 구조와 성장 단계

### 10.1 핵심 사용 흐름

```
GitHub 연동 → 레포 자동 분석 → 피드백(할 일 목록) + 트렌드 비교 확인
  → GitHub에서 직접 수정 → 다시 분석 → 체크 채워짐
  → 정리된 레포로 README · 이력서 · 프로젝트 카드 만들기
```

사용자 혼자서 처음부터 끝까지 완결되는 흐름이다. 다른 사용자가 없어도 가치가 생긴다.

### 10.2 성장 단계 — 커뮤니티는 언제 쓰나

커뮤니티를 버린 게 아니다. **순서를 바꿨다.**

| 단계 | 조건 | 중심 | 커뮤니티 기능의 역할 |
| --- | --- | --- | --- |
| 1단계 (지금) | 사용자 적음 | 레포 분석 · 피드백 · 트렌드 | 거의 노출 안 함 |
| 2단계 | 정리된 프로젝트가 쌓임 | + 탐방, Pofol 내부 트렌드 지표 | 피드: 다른 사람의 정리된 프로젝트 둘러보기, 북마크: 참고할 레포 모으기 |
| 3단계 | 활성 사용자 충분 | 커뮤니티 적극 활용 | 팀원 모집, 상호 피드백, 학과 쇼케이스 |

- **팀원 모집 · 북마크는 2~3단계를 위한 기능**이다. 지금은 유지만 하고 키우지 않는다.
- 1단계에서 쌓인 "정리된 프로젝트"가 2단계 피드의 콘텐츠가 된다. 빈 피드 문제를 개인 기능이 자연스럽게 해결한다.
- 사용자 데이터가 쌓이면 트렌드 분석에 **Pofol 내부 지표**가 추가된다 — 개인 기능과 커뮤니티가 이어지는 지점.
- 3단계 전환 기준(활성 사용자 수 등)은 운영 데이터를 보고 정한다.
